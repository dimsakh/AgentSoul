## [1.11.1] - 2026-07-27

Тема релиза: **публикация наружу была ручной операцией без записи и без проверки — и один раз уже утекла.**

### Fixed

- **Утечка в публичном репозитории: тег `v1.7.5` не был зачищен.** Дерево `main` (v1.10.0) чистили руками и оно чистое, но тег «Initial public release» от 2026-05-06 остался как был и доставался любым `git checkout v1.7.5`: личный email в `CHANGELOG.md`, имя пользователя ОС `/Users/…` в 5 файлах, имя и профиль конкретного человека, имя клиентского проекта в 5 файлах, ссылки на внутренний меморандум в 7. Цена решения: 3 звезды, страница прошлого release. URL сохранён.
- **Реальный NIP контрагента в примере `/enrich`.** В `skills/enrich/references/media-pass.md` как образец поискового запроса стоял настоящий налоговый номер клиентской компании. Пример обязан показывать форму запроса, а не данные конкретного контрагента. Найдено гейтом публикации на живом дереве, не глазами.
- **Реквизиты клиента в примерах `/wiki` и `/enrich`.** Почтовый адрес, часы работы, slug источника, город в шаблонах запросов. При публикации замена имени на плейсхолдер становится декоративной: по адресу и городу компания опознаётся независимо от того, как её назвали. Заменено на явно вымышленные значения того же формата.
- **Комментарии трёх стражей называли юридическую сессию клиента.** `bulk-copy-guard`, `internal-doc-leak-guard`, `user-correction-guard` выросли из одной сессии, и шапки описывали её прямо, хотя логика детекции доменно-нейтральна — привязка жила только в прозе. Рабочие слова детекции оставлены: по ним хук и работает.

### Added

- **`scripts/publish-public.sh` — повторяемая публикация с гейтом.** Приватная история непубликуема: в 269 коммитах лежат личный лог сессий и внутренний меморандум. Наружу уходит снимок дерева одним коммитом. Порядок: `git archive HEAD` → удалить пути из `exclude.txt` → применить `redact.sed` → **гейт по собранному дереву** → при `--push` пересоздать репозиторий, залить снимок, тег, release. По умолчанию — сухой прогон. Сборка из `HEAD` даёт побочное свойство: незакоммиченное не попадает в снимок по построению.
- **`scripts/publish/` — конфиг публикации в трёх декларативных файлах** (сам каталог не публикуется, в нём список реальных имён). `exclude.txt` — 16 путей внутренних документов и CI; `redact.sed` — карта замен, словарь взят из ручной зачистки v1.10.0 чтобы публичная версия читалась непрерывно от релиза к релизу; `forbidden.txt` — 22 шаблона, которых не должно быть на выходе.
- **`hooks/tests/test_publish_public.sh` — 23 ассерта.** Тест-файлов хуков 47.

### Почему скрипт, а не ещё одна ручная зачистка

`scripts/regen-seed.py` копирует frontmatter байт-в-байт из рабочей базы, поэтому имена клиентов в `source_cases` возвращаются в seed при **каждом** релизе. Разовая зачистка структурно не держится: её пришлось бы повторять вечно и проверять глазами. Уровень 3 embedded-ness по `principle-knowledge-in-the-world` — механическая проверка вместо текстового правила.

Защита двухступенчата, и это стоит понимать точно, чтобы не переоценить её. Для имён с правилом в `redact.sed` гейт ловит не сам токен — его успевает заменить шаг замен. Гейт ловит **сломанную замену**: выпало правило → исходное имя дожило до выхода → `forbidden.txt` загорелся. Для токенов без правила (имя человека, имя банковской папки, налоговый номер, UUID, секреты) гейт ловит их напрямую: тихая подмена скрыла бы сам факт, что личные данные занесли в дерево. Два файла конфига сторожат друг друга; тесты T2 и T2b проверяют обе ступени по отдельности.

Гейт работает **на выходе, а не на входе**, и считает собственные срабатывания: пустой `forbidden.txt` роняет прогон, а не проходит как «чисто». Это прямое следствие урока v1.11.0, где отсутствующий `timeout` возвращал 127 и пустой вывод читался как «зависаний нет» — инструмент не сработал, а его молчание засчиталось за отрицательный результат.

## [1.11.0] - 2026-07-25

Тема релиза: **система умела фиксировать стимул и не умела фиксировать реакцию; умела считать подтверждения и не умела считать опровержения.** Пока это так, любое утверждение о поведенческой устойчивости опирается на счётчик, который умеет только расти. Это релиз про измерительный прибор, не про новый слой.

### Added

- **`response-tracker.sh` (PostToolUse) — запись реакции агента.** Все прочие логи фиксируют стимул (сработал страж, инжектнулось знание, юзер поправил), ни один — что агент сделал следующим ходом; архитектура признаёт это формулой «детект ≠ комплаенс». Хук дописывает имя вызванного инструмента и путь файла в `state/response-<sid>.jsonl`, но **только после первого стимула в сессии** — до этого выходит по двум `[ -f ]`, без `jq` и без записи. Плюс `cleanupPeriodDays: 90` в `settings.json`: из 258 исторических событий блокера в архиве оставалось восстановимыми только 55, остальные сессии стёрты по сроку хранения. Тест `test_response_tracker` 12/12.
- **`backfill-compliance.sh` + `lib/backfill-compliance-one.py` — восстановление зависимой переменной из архива.** Разовый офлайн-прогон, только чтение. Три класса, все три обязательны: **A** — блокер `long_lived_markdown_doc_edit`, единица анализа интервал между двумя правками одного файла (маркер throttled на первую правку, поэтому поздние интервалы той же сессии образуют внутрисубъектный контроль); **B** — инжект знаний, event-study по расстоянию до действия; **C** — предупреждение о языке как **негативный контроль** (реагирует агент на содержание маркера или на факт его появления). Флаг `--verify-log` — гейт: сверяет восстановленное с `blocker-fired-*.jsonl` по 26 сессиям, где есть и то и другое. Скрипт намеренно **не считает p-value**: 441 интервал приходит примерно из 53 кластеров, наивный бином завысит значимость вдвое. Тест `test_backfill_compliance` 29/29 (включая три реальные грабли: каталог с ведущим дефисом, дубли attachment на один `toolUseID`, битая строка JSONL).
- **`knowledge-counter-bump.sh` — механический инкремент счётчиков знания.** `confirmed_count` / `contradicted_count`, `last_confirmed`, запись в `modification_history`; три формы поля истории (отсутствует / `[]` / блочный список) обрабатываются все, иначе запись молча теряется.
- **Producer контура опровержения в `knowledge-activator.sh`.** Читатель pending-записей существовал с v0.4.6, писателя не было ни одного дня: 0 файлов `disagreement-pending-*` на 1239 в `state/`. Точка выбрана в момент инжекта, а не в `blocker-tier-check`: там 89.9% срабатываний — один сигнал на правку четырёх markdown-документов одного проекта, встречи знания с решением в этом почти нет. Узко — только знания уровня блокера (3 файла), не все `confidence ≥ 4` (15 файлов): алерт, ставший фоном, не закрывают. Тест `test_disagreement_loop` 19/19.
- **Секция «Знание о себе» в еженедельном дайджесте.** Счётчики по консолидированному слою: надёжность, число уникальных **дат** в `source_cases` (прокси «пережило N независимых сессий», намеренно расходится с `confirmed_count`), последний вид модификации. Только счётчики, прозы нет по конструкции. Фильтра «про агента» нет намеренно: отбор по домену даёт согласие с ручной разметкой 67%, по `actors ~ agent` — 76%, оба ниже порога 80%, и оба теряют `pattern-completion-by-internal-proxy` (blocker-tier, знание буквально про поведение агента, но `actors: [system]`). `actors ~ agent` — колонка-маркер, не сито.
- **Правило hold-out в `knowledge/META.md`.** Множества «измеряемое» и «инжектируемое» не пересекаются. Знание о мире фальсифицирует мир; знание о себе, показанное экземпляру, становится инструкцией — инжект производит поведение, поведение записывается как подтверждение. Сегодня под правило подпадает `pattern-inside-out-blindness`: его `confirmed_count: 36` нельзя приводить как свидетельство устойчивости черты.
- **Поле `source_session`** в `knowledge/META.md` и обоих шаблонах кейса + страж утечки в `scripts/regen-seed.py` и `test_seed_integrity.py`: frontmatter копируется в публикуемый seed байт-в-байт, а публичный релиз v1.10.0 уже отложен из-за утечки личных данных (DEFER-1).

### Fixed

- **`metrics-collector.sh` считал по 285 строкам лога из 7665 и молчал об этом.** `jq -r '.file'` обрывался на первой битой строке, ошибка глушилась через `|| true`. Отчёт показывал 10 уникальных инжектированных знаний вместо 99, `hit_rate` 34% вместо 79%, средний score `n/a`. Устойчивый разбор `jq -rR 'fromjson? // empty'` (канонический паттерн проекта), числитель `hit_rate` сужен до `pattern-*|principle-*` через пересечение с диском — иначе починка дала бы 341%, потому что в логе есть ещё `case`/`fact`/`relation` от mcp-fallback. Средний score считается без синтетической `99`. Добавлена строка «⚠️ Битых строк в injection-log: N» — её отсутствие и позволило багу прожить три месяца с правдоподобным числом.
- **Корень 173 битых строк — утечка `|` из поля `name`.** `|` служит разделителем протокола `RESULTS`, а у знания `case-2026-04-15-grep-set-e-crash` в названии стоит `||`: поля разъезжались до записи, `confidence` принимал значение куска описания. Санитизация на обеих границах рождения pipe-строки (`knowledge-semantic-fallback-lib.sh`, извлечение `NAME`/`DESC`), запись лога переведена с `printf` на `jq -Rcn`. Историческую миграцию 173 строк **не делаем**: вся её цена — единица в справочном счётчике, а цена — перезапись живого append-файла, в который в тот же момент пишет PreToolUse-хук.
- **Детектор смешения алфавитов считал нарушением обычные дефисные композиты.** `dev-БД`, `API-роут`, `Telegram-бот` — 2524 из 2689 срабатываний (94%), при 79 целевых случаях внутрисловного смешения. Метрика была в 34 раза шумнее сигнала, и класс событий не годился как измерение. Дефис теперь считается границей слова, апостроф — нет (`fix'ом` остаётся нарушением). На исторических данных 2689 → 175 срабатываний. Тест `test_output_language_detect` 17/17.
- **`knowledge-activator.sh` падал под `set -u`, когда keyword-скоринг не нашёл ничего** — то есть ровно в случае, ради которого существует семантический откат. `"${RESULTS[@]}"` на пустом массиве в bash 3.2 (системный на macOS) считается обращением к unset. Найдено новым тестом, не в проде.
- **Запрет в `/learn` Step 4a, из-за которого `contradicted_count` был равен нулю во всех 265 знаниях.** Правило «при противоречии НЕ трогать автоматически, нужен `/retro`» держало счётчик пустым при 156 знаниях с подтверждениями, а `/retro` писал соседнее поле, которое тоже осталось нулевым по всем 13 файлам. Инкремент теперь механический (скрипт), решение о судьбе знания по-прежнему в `/retro`. Добавлен Step 4e — закрытие pending-исхода с тремя вариантами, включая `not_applicable` («знание всплыло не к месту» — тоже измерение, оно говорит о якорях знания).

Если stdin — открытая труба, которую никто не закроет (типичный запуск из обёртки, хук-раннера, CI), `cat` ждал вечно. `hooks/tests/run_all.sh` вставал на 10 минут и выглядел при этом как «тесты идут». ### Security

- **Закрыт сетевой `delete` в viz-сервере (`mcp-server/visualization/serve.py`).** Сервер визуализации графа имеет мутирующие POST-эндпоинты (`/api/node/{open,archive,delete}`, где `delete` → `path.unlink()` необратимо). Две дыры: (1) bind на `("", port)` = `0.0.0.0` — любое устройство в локальной сети могло удалять файлы знаний; (2) POST не проверял `Origin` — любой сайт в браузере мог cross-origin удалить узел (CSRF; `json.loads` парсит и `text/plain` без preflight). Фикс: bind на `127.0.0.1` (только loopback) + Origin-гейт на POST (403 на чужой Origin; не-браузерные клиенты без `Origin` проходят). Заодно тело запроса читается один раз вверху `do_POST` — все ветки ответа (403/404/200/400) закрывают соединение с корректным `Content-Length` (раньше 404-ветка оставляла тело непрочитанным → RST). Path-traversal guard (`_resolve_node_path` — удаление только внутри `global-lessons`) был и остаётся. ## [1.7.4] - 2026-05-06

**🛡️ install.sh CLAUDE.md merge — marker-based**

### Проблема

`install.sh::CLAUDE.md handling` сломан by design с момента проекта. Старая логика:
- if grep -q "Self-Learning" → SKIP (master changes никогда не propagate в deployed)
- elif file exists → cat master >> deployed (дублирование на rerun)

Симптом: после v1.6.8 при правке `rules/CLAUDE.md` приходилось вручную делать `cp master deployed` после backup — не масштабируется на чужих машинах.

### Fix

Marker-based merge. Master content в deployed обёрнут в `<!-- ClaudSoul: managed-start -->` ... `<!-- ClaudSoul: managed-end -->`. `install.sh` заменяет ТОЛЬКО содержимое между маркерами; контент пользователя снаружи сохраняется.

4 случая:
1. Markers есть → replace between (sync from master)
2. Legacy без маркеров с "Self-Learning" → переписать с маркерами + backup
3. User content без признаков ClaudSoul → append блок с маркерами + backup
4. Файла нет → создать с маркерами

Каждое изменение оставляет `${target}.bak.YYYYMMDDHHMMSS`.

### Архитектура

Логика merge извлечена в `lib/claude-md-merge.sh` (sourceable). install.sh источит и вызывает `sync_claude_md`. Это позволяет тестировать функцию напрямую.

### Тесты

`hooks/tests/test_claude_md_merge.sh` — **26/26** пройдено. Покрывают 4 случая + idempotency двойного вызова + missing master returns 1. Полный suite: 23/23 файла зелёные, 781 ассерт.

### Принцип

`install.sh` — single source of truth для deployed configuration. Skip-on-existing лечит симптом (нет дубликации) ценой проблемы (sync ломается). Marker-based merge даёт оба свойства: idempotent + sync.

## [1.7.1] - 2026-05-06

**🔧 reformulation-tracker SIGPIPE fix**

### Симптом

«UserPromptSubmit hook error — Failed with non-blocking status code: No stderr» на каждом сообщении пользователя.

### Корневая причина

В `reformulation-tracker.sh:78` использовался паттерн `tail -r FILE | while ... break ... done` для чтения последнего assistant сообщения из транскрипта. Когда while делает break, читающая сторона pipe закрывается до того как tail успевает прочитать весь файл — tail получает SIGPIPE и завершается с exit 141.

С `set -eo pipefail` (line 22) этот 141 становится exit code всего pipeline, а `set -e` сразу убивает скрипт. Stderr пустой — потому что SIGPIPE не печатает сообщений.

### Fix

Обернуть проблемный pipeline в `set +o pipefail` ... `set -o pipefail`, чтобы SIGPIPE на tail не приводил к ненулевому exit всего pipeline.

Verified: тест с реальным 2.8 МБ транскриптом — exit 0 (было 141).

### Принцип

Backfill производит данные в нативном формате детектора (raw events, per-turn). Калибратор работает на агрегатах (digest, per-session). Между ними — фиксированная схема mapping. Mapping должен быть явно прозрачным: какие поля derivable из raw events, какие — нет (zero с маркером source: backfill, чтобы будущий читатель видел что эти zero — не наблюдение, а отсутствие proxy).

Это не «backfill полностью эквивалентен live» — это «backfill даёт subset полей, достаточный для конкретной калибровочной задачи». Subset включает критичное для v1.4.0: gentle/proactive acceptance rate, budget ceiling hits, events count distribution. Не включает H11 (`backward_count`) — это блокер v1.7, требует отдельного backfill через reformulation-tracker.

### Что сделано

  proactive:    497 (300 accepted, 197 ignored) → acceptance rate 60%

### Валидация in-loop

Этот коммит сам проходит через исправленный pipeline: `docs-family-check.sh` теперь физически установлен и включён в `settings.json` → срабатывает на `git commit` PreToolUse, проверяет staged diff на coverage docs family (architecture + PLAN + CHANGELOG + README + project CLAUDE.md). Если хоть один файл не обновлён с version marker — silent inject `🛑 Docs family drift: missing <список>`. Fix валидируется как одна транзакция — хук, который он включает, проверяет сам коммит.

### Принцип

Fix после подтверждённого инцидента обязан учитывать **all four levels of embedded-ness**: text rule → activator injection → blocker-tier hook → **proof-of-active**. Запись в коде + регистрация в install.sh + test green — это только первые три уровня. Четвёртый — механическая сверка installed vs registered vs repo в startup pipeline. Без него любой новый хук между релизами попадает в silent divergence, и «работает» становится ложным claim'ом CHANGELOG. Текстовое правило «не забудь запустить install.sh после добавления хука» — по конструкции исключено (уровень 1 для этого класса failure mode).

### Разрыв

`v1.3.9` поставил базовый cross-contour consumer: knowledge-activator читал `cross-contour-discoveries.jsonl` и surfaced пары `knowledge ↔ entity` только тогда, когда **тот же `knowledge_file` уже попадал в текущий инжект-набор**.
